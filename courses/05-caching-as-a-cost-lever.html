Caching as a cost lever

Session 1 found that most of Kiln's prompt is the same 1,200 tokens on every request. A cache can stop paying full price for that repeat, but only if the prompt is laid out so the repeat comes first, only if it is long enough to qualify, and only if requests arrive often enough to hit it. Tonight we treat caching as a design decision rather than a line on the invoice: the provider's prompt cache, the same idea inside your own serving engine, and the answer cache that saves the most and is the only one that can hand a user the wrong answer.

Part 1 · covers prompt layout for prefix hits

The cache matches from the first token

5 min live

A prompt cache stores the work already done on the beginning of a prompt and reuses it when a later prompt begins with exactly the same tokens. Matching starts at token one and stops at the first difference. So a single changing token near the start, a name or a timestamp, makes everything after it a miss, however much of the rest is identical.

LiveWhat both big providers say about order3 min▶

OpenAI's prompt caching guide, read on 2026-11-08, says caching is "enabled by default for supported OpenAI models" and advises putting "stable developer instructions and shared reference material first", with timestamps and user-specific content at the end. Anthropic's guide says "Cache prefixes are created in the following order: tools, system, then messages", lets you mark "up to 4 cache breakpoints", and keeps an entry for 5 minutes by default. Different mechanics, same rule: the stable part goes first and the changing part goes last.

For Kiln that means moving the greeting with the user's name and the date out of the top of the prompt and into the last user message, after the 1,200 tokens of rules and tools. The model sees the same information; the cache sees a repeat.

LiveTwo ways a cache silently never engages3 min▶

Too short. Providers only cache prefixes above a minimum length. Anthropic's minimum, read on 2026-11-08, is 1,024 tokens for Claude Sonnet 4.5 but 4,096 for Claude Haiku 4.5. Kiln's 1,200-token prefix qualifies on Sonnet and never qualifies on Haiku: the bench prints "The cache never engages" for Haiku 4.5 with the static-first layout, and the cost stays $2.55 per 1,000. OpenAI's minimum is 1,024 tokens for GPT-5.6 and later and "varies by request settings for earlier models".

Too rare. Entries expire. OpenAI keeps in-memory entries for "around 5 to 10 minutes of inactivity, up to one hour"; Anthropic's default is 5 minutes. A prompt seen twice an hour is a miss every time. Low-traffic features, or prompts split into many variants, get little from caching however well they are laid out.

Part 2 · covers the write premium and KV prefix reuse

A cache hit is cheap; a cache write may not be

5 min live

Providers price a cached prefix two ways. OpenAI discounts cached input with no charge for writing it: gpt-4.1's cached input is $0.50 per million against $2.00. Anthropic charges a premium to write the cache and a deep discount to read it: 1.25 times the base input price to write a 5-minute entry and 0.1 times to read it. With a write premium, a cache that rarely hits costs more than no cache at all.

LiveWhere the 21.7% comes from2 min▶

Every miss writes the prefix at 1.25 times the base price; every hit reads it at 0.1 times. Caching beats paying full price when the average multiplier is under 1: hit rate times 0.1 plus miss rate times 1.25 below 1. That solves to a hit rate above 0.25 / 1.15, which the widget prints as 21.7%. At 10% hits Kiln pays $8.13 per 1,000 requests against $7.65 uncached; at 90% it pays $4.82, 37.0% less. On gpt-4.1, with no write premium, any hit at all saves money: $2.98 against $4.60 at 90%.

Your hit rate is a property of your traffic, not of the provider: how many requests share the prefix within the cache's lifetime. Read it from the cache-read token counter on your usage reports. Learn AI Observability covers that accounting and the traps in it (what AI costs you ↗, cost and latency per span ↗).

LiveThe same idea inside your own engine3 min▶

When you serve the model yourself, the cache is the key-value cache from session 4, kept after a request ends and reused by the next request with the same prefix. vLLM's automatic prefix caching, read on 2026-11-08: "we hash each kv-cache block by the tokens in the block and the tokens in the prefix before the block", "We only cache full blocks", and the least recently used block is evicted first. SGLang keeps the cache "for both prompts and generation results in a radix tree" with leaf-first eviction (LMSYS blog, 2024), and its paper calls this RadixAttention.

Here the saving is not a discount on a bill but prefill you no longer do. On the bench's model of one L4 with FP8 weights, turning the prefix cache on cuts Kiln's p95 time to first token at 0.25 requests a second from 656 ms to 174 ms, and raises the highest load meeting the 1 s target from 0.75 to 1.5 requests a second, which halves the cost per 1,000 requests from $0.30 to $0.15. Modelled, and optimistic: vLLM's own reported speed is slower than the roofline.

Real world

Two numbers for one system. The SGLang paper (Zheng et al., arXiv:2312.07104) reports "up to 6.4x higher throughput compared to state-of-the-art inference systems"; the LMSYS blog post that introduced it reported "up to 5 times higher throughput compared to existing systems". Both are the authors' own benchmarks at different times. Prefix reuse pays most when many requests share long prefixes, agents and few-shot templates especially, and close to nothing when every prompt is unique. Measure your own sharing before you believe either.

Part 3 · covers the answer cache

The cache that can be wrong

5 min live

A prompt cache only reuses work; the model still answers every request fresh. An answer cache, often called a semantic cache, skips the model entirely: it embeds the new question, looks for a stored question that is close enough, and returns that question's stored answer. It saves the whole request, input and output. It is also the only cache here that can return an answer to a question nobody asked.

LivePrice the wrong answers, not only the hits3 min▶

The bench runs Kiln on Claude Sonnet 4.5 with the static-first prompt at 90% prefix hits ($4.82 per 1,000) and then adds an answer cache in two constructed settings. Short expiry, 10% of requests answered from the cache with 2% of those hits wrong: $4.34 per 1,000, 43.3% under no caching, and 2.0 wrong cached answers per 1,000 requests. Long expiry, 25% hits with 8% of hits wrong: $3.61, 52.7% saved, and 20.0 wrong answers per 1,000.

Those hit and error rates are invented to show the shape; nobody can tell you yours without labelled pairs from your own traffic. The shape is the lesson: the setting that saves most also serves ten times the wrong answers. Kiln's 95% quality floor from session 2 applies here too: 20.0 wrong per 1,000 is two percentage points of quality spent on a cache, on top of whatever the router already spends.

Self-studyWhere an answer cache is safe3 min▶

Exact-match caching of identical requests (same prompt, same parameters, deterministic settings) has no wrong-answer risk beyond staleness and is worth doing for repeated batch jobs. Similarity matching is safest where answers do not depend on who asks or when: public product documentation, help-centre questions, definitions. It is riskiest where a near-identical question has a different answer: account balances, anything with a date, anything personal. Give every entry an expiry tied to how often its source facts change, and log every cached answer served so a wrong one can be traced.

Homework

Before session 6

30 min
  1. Draw your own prompt as blocks in the order it is sent, and mark the first block that changes between two users. Everything after it is uncacheable today.
  2. Check your prefix against your model's minimum cacheable length on your provider's current caching page.
  3. Read your cache-read token counter for a week and compute your real hit rate. If your provider charges a write premium, compare it with your break-even.
  4. Collect 50 pairs of near-identical questions from your logs and mark which ones need different answers. That count is the beginning of an answer-cache error rate.
Check yourself

Three questions

Clear all three and session 5 gets stamped in your passport.

1 · Kiln's prompt starts with the user's name and the date, then 1,200 tokens of fixed rules. What does a prompt cache save?

A prefix cache reuses work only up to the first differing token. With the name and date first, no two requests share a prefix, and the bench prints no saving at any hit rate until the layout is static first.

2 · On Claude Sonnet 4.5 (write 1.25x, read 0.1x), at what prefix hit rate does caching stop losing money?

Caching wins when hit rate x 0.1 + miss rate x 1.25 is under 1, which is a hit rate above 21.7%. At 10% hits Kiln pays $8.13 per 1,000 against $7.65 uncached. With no write premium (gpt-4.1), any hit saves.

3 · Why does the memo hold back the answer cache even though its long-expiry setting saves 52.7%?

Prompt and prefix caches reuse work but the model still answers each request. An answer cache returns a stored answer, which can be stale or meant for a different question. Until its error rate is measured on labelled pairs, its saving is not comparable with the quality it spends.
