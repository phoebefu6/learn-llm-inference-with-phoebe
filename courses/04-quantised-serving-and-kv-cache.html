Learn LLM Inference and Model Serving with Phoebe · Session 4 of 6

Quantised serving and the KV cache

A GPU does not run out of arithmetic first. It runs out of room. The weights take a fixed slab of memory, and every request in flight takes more on top, a few hundred kilobytes for every token it has read or written. Whatever is left after the weights decides how many requests one GPU can hold at once, and that number decides what each request costs. Tonight we measure the cache in bytes, see why paging it changed serving, shrink the weights and the cache, read the quality bill, and fit Kiln's model onto one L4.

Part 1 · covers KV memory per token

Every token rents memory

5 min live

Session 1 described the KV cache in a paragraph: for every token a request has read or written, every layer keeps one key vector and one value vector so decode never re-reads the prompt. Now put a size on it. The formula needs four numbers from the model's config file and one from your chosen precision: KV bytes per token = 2 (key and value) x layers x KV heads x head dim x bytes per number.

LiveRead the formula off a config file3 min▶

Llama 3.1 8B's published config.json (read from the unsloth mirror, because meta-llama's own copy is gated) lists 32 layers, 8 key-value heads and a head dimension of 128. In BF16 each number is 2 bytes. So one token costs 2 x 32 x 8 x 128 x 2 = 131,072 bytes, which is 128 KB. Llama 3.1 70B, with 80 layers and the same 8 KV heads, comes to 320 KB. Qwen2.5 7B, with 28 layers and only 4 KV heads, comes to 56 KB (all three computed from their configs).

Multiply by context length and by requests in flight and the cache becomes the thing that fills the GPU. On an L4, 90 percent of 24 GB is usable in the bench, 21.6 GB. The BF16 weights take 16.1 GB, the runtime holds back 1.5 GB, and the KV pool gets 4.0 GB: 30,818 tokens, or 19 requests at Kiln's mean 1,588 tokens of prompt plus answer (modelled; the widget prints each of these). vLLM's own --gpu-memory-utilization default is now 0.92; the bench rounds down to 90 percent.

Real world

The PagedAttention paper did the same sum. Kwon et al. (2023) work it for OPT-13B: one token's KV state is "2 x 5120 x 40 x 2" bytes, 800 KB, and a single 2,048-token request "can be as much as 1.6 GB". On an A100 40GB serving that 13B model, about 65 percent of memory goes to weights and close to 30 percent to the KV cache. Same arithmetic as Kiln's figure above, a bigger model and a bigger GPU.

Self-studyWhy Llama's cache is small: shared KV heads3 min▶

Llama 3.1 8B has 32 attention heads for queries but only 8 KV heads: groups of query heads share one key and one value. The formula only counts KV heads, so the cache is a quarter of what 32 full heads would cost. Pope et al. (2022) took the idea to its limit with multiquery attention, one shared KV head, and report it enables scaling to "32x larger context lengths". Qwen2.5 7B shares even harder, 28 query heads on 4 KV heads, which is why its 56 KB per token is under half of Llama's 128 KB.

The habit to keep: before you pick a model for a long-context feature, open its config file and compute this number. Two models of the same parameter count can hold very different numbers of requests on the same GPU.

Part 2 · covers PagedAttention

Reserve what you use, not what you might

5 min live

A serving engine does not know how long an answer will be when the request arrives. The simple fix is to reserve the maximum for every request up front: a contiguous slot big enough for the longest sequence allowed. Most answers end long before the slot is full, so most of that reservation sits empty, and the GPU turns away requests it has room for. Paging fixes it the way an operating system does: hand out memory in small fixed blocks as each request's tokens arrive.

LiveWhat the paper found, in its own words3 min▶

Kwon et al. (2023), "Efficient Memory Management for Large Language Model Serving with PagedAttention" (SOSP 2023), measured the systems that came before: they used "only 20.4% - 38.2% of the KV cache memory" to store actual token states. The rest was reserved space that never filled and gaps between reservations. Their fix stores each request's keys and values in fixed-size blocks that need not sit next to each other, the way virtual memory pages work, and reaches "near-zero waste in KV cache memory". With more requests in each batch, vLLM "improves the throughput of popular LLMs by 2-4x" against FasterTransformer and Orca.

Popular summaries of this paper often carry waste percentages that are not in its text. When you cite it, quote the 20.4% - 38.2% line and the 2-4x line, which are.

Real world

Paging went from paper to default. vLLM's own PagedAttention design page now describes itself as "a historical document": the idea is simply how the engine works. NVIDIA's TensorRT-LLM lists a "Paged KV cache with intelligent block reuse" among its features. And because memory now lives in blocks, a block of a shared prefix can be found and reused: vLLM's automatic prefix caching hashes each block by its tokens and the tokens before it. That reuse is session 5's lever.

Self-studyKiln's paging bench, modelled4 min▶

Hold everything else still: L4, Llama 3.1 8B with FP8 weights, continuous batching. The bench's reserved mode gives every request a 4,096-token slot; its paged mode reserves only each request's own final length. Same 92,084-token pool. Reserved holds 22 requests, paged holds 57. Run the load sweep and the highest load meeting Kiln's 1 s p95 first-token target is 0.5 requests a second reserved against 0.75 paged, which prices out at $0.44 against $0.30 per 1,000 requests (all modelled).

The bench's paged mode is kinder than it should be in one way and harsher in another. It knows each request's final length on admission, which a real engine does not, and it never preempts a request when memory runs short, which a real engine does. Treat the gap between 22 and 57 as the shape of the effect, not a forecast for your traffic.

Part 3 · covers quantised weights and KV

Smaller weights, more room, and a quality bill

5 min live

Quantisation stores each number in fewer bytes: BF16 uses 2, FP8 and INT8 use 1, and INT4 weight-only uses half a byte while the arithmetic still runs in 16-bit. Smaller weights do two things at once on a decode-bound GPU. Each step has fewer bytes to stream, so it is faster, and the memory they free goes to the KV pool, so more requests fit. The cache itself can be stored in FP8 too, which halves the bytes per token. The price is paid in answer quality, and how big that price is depends on who you ask.

LiveWhy INT4 and an FP8 cache stop paying at 0.754 min▶

Read the bench's four L4 rows (all modelled). BF16: 16.1 GB of weights, 19 requests, 90.4 ms per token for one request alone, max load 0.25 requests a second at the 1 s target, $0.89 per 1,000 requests. FP8 weights: 8.0 GB, 57 requests, 45.8 ms, 0.75 requests a second, $0.30. INT4 weight-only: 4.0 GB, 77 requests, 23.5 ms, still 0.75, still $0.30. FP8 weights plus an FP8 KV cache at 64 KB per token: 115 requests, still 0.75.

The first step pays because BF16 was memory-starved: 19 requests cannot form a big enough batch. After FP8 the binding limit moves. Kiln's target is on time to first token, and every request still has to prefill its 1,200-token system prompt plus the question; INT4 weight-only still computes in 16-bit, so prefill does not get faster. At the next load the sweep tries, 1 request a second, the p95 is 1.25 s for FP8, 1.09 s for INT4 and 1.16 s for FP8 with an FP8 cache. All three miss the 1 s line. More room for requests does not help when the queue and prefill are what make the first token late. Session 5 attacks exactly that prefill.

The model is a roofline plus a seeded queue: it says 8.1 ms per token for this model alone on an H100, against the "1 token every 13 ms under light load" that vLLM's 2024 performance post reports. Read every capacity number here as optimistic.

Real world

Teach the disagreement: how much quality does a smaller number cost? Kurtic et al. (2024), "'Give Me BF16 or Give Me Death'? Accuracy-Performance Trade-Offs in LLM Quantization" (ACL 2025), ran over 500,000 evaluations on the Llama-3.1 family and report that "FP8 (W8A8-FP) is effectively lossless across all model scales", that "well-tuned INT8 (W8A8-INT) achieves surprisingly low (1-3%) accuracy degradation", and that "INT4 weight-only (W4A16-INT) is more competitive than expected, rivaling 8-bit". NVIDIA's TensorRT-LLM says FP8 "can double performance and halve memory consumption compared to 16-bit". Practitioners still report task-specific drops that benchmark averages hide. Both can be true: an average across tasks can be flat while your one task falls. The working rule is the same either way: run your own eval at the precision you will serve.

Self-studyHow the 4-bit methods keep quality4 min▶

Rounding every weight to 4 bits naively hurts. Two methods made weight-only 4-bit practical. GPTQ (Frantar et al., ICLR 2023) quantises one layer at a time and corrects the remaining weights for each rounding error; it quantised a 175B model "in approximately four GPU hours" to 3 or 4 bits. AWQ (Lin et al., MLSys 2024) observes that a few weights matter far more than the rest: "Protecting only 1% salient weights can greatly reduce quantization error".

Kurtic et al. also add a deployment twist: "W4A16 is the most cost-efficient for synchronous setups, while W8A8 dominates in asynchronous continuous batching". That matches the bench's shape. INT4 makes a lone request's decode fastest (23.5 ms against 45.8 ms), but under continuous batching at Kiln's target the two land on the same 0.75 requests a second.

Training-time 4-bit is a different job. The fine-tuning sessions work weights memory by hand (small models and their trade-offs ↗) and use 4-bit base weights to train adapters cheaply (LoRA and QLoRA ↗). Here the question is only what you serve.

Self-studyWhere the quantised formats come from3 min▶

vLLM's quantization docs list the formats it loads, each with its own tooling: AutoAWQ, BitsAndBytes, GPTQModel, LLM Compressor (FP8 W8A8, INT4 W4A16, INT8 W8A8), a quantized KV cache, TorchAO and GGUF among them. Check which formats your GPU generation supports before you pick one: the FP8 tensor-core path needs recent hardware, and the bench does not model FP8 arithmetic speedups at all, only the smaller bytes. DeepLearning.AI's "Quantization Fundamentals with Hugging Face" and "Quantization in Depth" short courses walk through the number formats by hand if you want the arithmetic underneath.

Build-along

Fit Kiln's model and its cache on one GPU

★ 22 min · everyone builds

Constructed Kiln example, real request lengths. The capacity widget takes a GPU, a model, a weight precision, a KV precision and a memory mode, does the fitting arithmetic, then runs a seeded queue of 1,000 requests with the real RouteLLM prompt and answer lengths plus Kiln's 1,200-token system prompt. Every capacity number it prints is modelled. Your job is to find the cheapest setting that meets Kiln's 1 s p95 first-token target, and to write down what it still owes in quality.

The capacity widget

It opens on the L4 with Llama 3.1 8B in BF16 at 0.25 requests a second. It prints weights in memory, KV cache per token, the KV pool, concurrent requests, decode time for one request alone and the p95 time to first token; the "Run the load sweep" button adds the max load meeting the 1 s target and its cost per 1,000 requests.

Read the starting point, then run the sweep. L4, Llama 3.1 8B, BF16 weights, BF16 KV cache, continuous batching, paged. Write down the five memory tiles, then press "Run the load sweep".

Write Kiln's serving line. One sentence Maya can take to Theo, with the condition attached. The 8B on the L4 is the small side of the router from session 2, so the eval belongs on that easy traffic, with the model you will actually serve; the routing quality rows were measured on a different small model, Mixtral 8x7B.

★ Step 6 · Kiln's lineSmall side: Llama 3.1 8B, FP8 weights, BF16 KV cache, paged, on one L4: 57 requests in memory, 0.75 req/s at the 1 s target, $0.30 per 1,000 requests (modelled, optimistic). Condition: run our own eval at FP8 on the requests the router sends small, before shipping. INT4 and an FP8 cache add room, not load, at our target; revisit only if the target changes.

Your numbers will differ. Your mean context sets how many requests fit, and your latency target decides whether memory or prefill is the wall. Compute KV bytes per token from your own model's config, divide your pool by your own mean prompt plus answer, and load-test one GPU before you trust any of it.

Homework

Before session 5

30 min
  1. Compute KV bytes per token for the model you serve or plan to serve, from its config.json: 2 x layers x KV heads x head dim x bytes. Note how many KV heads it shares across its query heads.
  2. Do the fitting arithmetic for your GPU: usable memory, minus weights, minus a runtime reserve, divided by KV per token, divided by your own mean prompt plus answer length from a week of logs.
  3. Find which limit binds for you: in the widget, set the settings nearest yours and run the sweep at two precisions. If the max load does not move, memory is not your wall.
  4. Write a quantisation eval plan: twenty to fifty of your real requests, the quality bar you already use, and the precision you would serve. Run it before you change precision, not after.
Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · Qwen2.5 7B has 28 layers, 4 KV heads and a head dimension of 128. In BF16, how many bytes of KV cache does one token take?

The formula counts key and value (2), layers, KV heads (not query heads), head dimension and bytes per number. For Qwen2.5 7B that is 56 KB, under half of Llama 3.1 8B's 128 KB because it shares 4 KV heads instead of 8.

2 · With the same FP8 weights and the same 92,084-token pool on an L4, why does paged KV memory hold 57 requests where reserved slots hold 22?

Bytes per token are unchanged; what changes is the bookkeeping. Kwon et al. found earlier systems used only 20.4% - 38.2% of KV memory for actual token states. Paging stops empty reservations from blocking new requests, so more of them share each weight read.

3 · What did Kurtic et al. (2024) report for INT4 weight-only quantisation on the Llama-3.1 family?

The paper calls FP8 "effectively lossless", puts well-tuned INT8 at 1-3% degradation, and says INT4 weight-only is "more competitive than expected, rivaling 8-bit". Practitioners still see task-specific drops, so run your own eval at the precision you serve.
