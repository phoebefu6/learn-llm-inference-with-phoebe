Learn LLM Inference and Model Serving with Phoebe · Session 1 of 6

Where the money and the milliseconds go

Every request to a language model is two different jobs glued together. First the model reads your whole prompt in one pass, which keeps the GPU's arithmetic busy. Then it writes the answer one token at a time, and for every single token it has to stream all of its weights out of memory again. The first job sets how long the user waits for the first word; the second sets how long the rest takes and why output tokens are priced higher. Tonight we take one request apart and split Kiln's real request mix into the two budgets.

Part 1 · covers prefill and decode

One request, two jobs

5 min live

A model generates text one token at a time, and each new token depends on all the tokens before it. The prompt, though, is already known when the request arrives, so the model can process all of its tokens at once in a single pass. That pass is called prefill. It ends with the first output token. Everything after it is decode: one forward pass per token, each pass producing exactly one more token, until the answer is done.

LiveTwo latency numbers, not one3 min▶

Serving engines report two numbers and so should you. Time to first token (TTFT) is the wait from sending the request until the first word appears: time in the queue plus the prefill pass. Time per output token (TPOT, sometimes inter-token latency) is the gap between later tokens: one decode step. Total latency is roughly TTFT plus TPOT times the number of output tokens.

They respond to different levers. A longer prompt raises TTFT and barely touches TPOT. A longer answer leaves TTFT alone and multiplies TPOT. A crowded server raises both, through the queue and through bigger batches. When Kiln's p95 first-token time doubled, the honest first question was which of the three moved. Learn Agent Launch treats TTFT and total latency as service levels you set and watch; here we take apart the mechanism behind them (operational metrics ↗).

Self-studyThe KV cache, in one paragraph3 min▶

Why can decode produce one token per step without re-reading the whole prompt each time? Because prefill saves, for every prompt token and every layer, two vectors called the key and the value. Each decode step adds one more key and value per layer and attends over all the saved ones. That saved store is the KV cache. It is what makes decode cheap in arithmetic, and it is also what fills GPU memory as requests and answers grow. Session 4 measures it in bytes per token and shows how it caps the number of requests one GPU can hold.

Part 2 · covers compute-bound against bandwidth-bound

What each job waits on

5 min live

A GPU has two limits that matter here: how many multiply-adds it can do per second, and how many bytes per second it can move from its memory to its arithmetic units. Prefill does a lot of arithmetic for every weight it reads, because it pushes 1,300 tokens through each weight in the same pass, so it runs into the arithmetic limit. Decode, with one request, pushes one token through each weight, so the arithmetic finishes long before the next weights arrive: it waits on memory bandwidth.

LiveThe arithmetic you can do on a napkin3 min▶

Llama 3.1 8B has 8,030,261,248 parameters, computed from the shapes in its published config file: 32 layers, hidden size 4,096, 8 key-value heads. At two bytes each (BF16) that is 16.1 GB. To produce one token alone, the GPU must move all 16.1 GB through a pipe NVIDIA's spec sheet rates at 300 GB/s on an L4. Even at full speed that is over 50 milliseconds; the bench assumes 60 percent of the rated bandwidth is achieved and prints 90.3 ms per token. On an H100 (3.35 TB/s) the same arithmetic prints 8.1 ms.

Prefill is the opposite case. Every weight read is used for 1,300 tokens, so the arithmetic, about two operations per parameter per token, becomes the slow part: the bench prints 345 ms to prefill Kiln's mean prompt on an L4 and 42 ms on an H100. These are a model, a roofline, not a measurement. vLLM's own 2024 performance post reports Llama 3 8B generating "1 token every 13 ms under light load", against the bench's 8.1 ms on an H100, so read the model as optimistic.

Real world

Google's numbers for a 540-billion-parameter model. Pope et al. (2022), "Efficiently Scaling Transformer Inference", report "29ms per token during generation (using int8 weight quantization)" at low batch size, and "76% MFU during large-batch-size processing of input tokens". Same model, same hardware, two regimes: generation measured as time per token, input processing measured as how fully the arithmetic units are used. That split is the prefill and decode split.

Self-studyWhy batching is the escape hatch3 min▶

If one decode step reads 16.1 GB to make one token, the same read could make one token for each of 30 requests at almost the same cost, as long as their key-value caches also fit. That is the whole economic case for batching, and it is why a GPU serving one user at a time is mostly idle arithmetic. Session 3 runs the queue and shows the price: bigger batches raise throughput and push the tail of first-token latency out.

Part 3 · covers the price list

Why output tokens cost more

5 min live

API price lists charge per million tokens, with a separate, higher price for output. On OpenAI's list read on 2026-11-08, gpt-4.1 is $2.00 per million input tokens and $8.00 per million output; Anthropic's Claude Sonnet 4.5 is $3 and $15. The ratio is four to five. The mechanism above is the reason: an input token rides along in one parallel pass, while every output token is a full step of its own.

LiveRead your own bill in two lines3 min▶

Every provider dashboard splits usage into input and output tokens. Multiply each by its price and you know which lever to pull first. Kiln's split is close to even: 56.5 percent input, almost all of it the 1,200-token system prompt repeated on every request, and 43.5 percent output. That tells Maya two things at once. The repeated prompt is a caching target (session 5), and the answers are a routing and serving target (sessions 2 to 4). A team whose answers are long essays would see the split tilt hard towards output, and caching would matter less.

Real world

The batch discount is the same mechanism, priced. OpenAI's Batch API, read on 2026-11-08, offers a "50% cost discount compared to synchronous APIs" for work that can wait: "Each batch completes within 24 hours (and often more quickly)". Anthropic's Message Batches carry "a 50 percent discount on both input and output tokens". Requests that can wait can be packed into big batches on the provider's side, which is the cheapest way to run decode. Kiln's nightly summary emails are a candidate; its in-app chat is not.

Self-studyLong contexts move the balance3 min▶

Each decode step also reads the key-value cache of the request it is serving, and that cache grows with every prompt and answer token. At short contexts the weights dominate the read; at long contexts the cache can rival them. That is one reason long-context requests are slower per token and why some price lists charge more above a context threshold. Session 4 shows the KV cache in bytes and the bench lets you watch the step time rise as sequences grow.

★ Step 4 · Maya's two budgetsPrefill budget: 1,300 tokens per request, 1,200 of them identical. Lever: stop paying full price for the repeat (session 5). Your numbers will differ. Swap in your own mean prompt and answer length from a week of logs: the input share and the decode-to-prefill ratio are the two lines worth keeping. If your answers are long and your prompts short, decode dominates and caching will not save much.

Check yourself

Three questions

Clear all three and session 1 gets stamped in your passport.

1 · Kiln adds 2,000 tokens of policy text to every prompt. Which latency number rises most?

Prefill processes every prompt token before the first output token can appear, so a longer prompt lengthens time to first token. Decode steps also read a slightly larger key-value cache, so time per token rises a little, but the first-token wait moves most.

2 · Why does one decode step take about as long for one request as for a handful?

With one request, a decode step moves all 16.1 GB of Llama 3.1 8B's BF16 weights to make one token; the arithmetic idles. Several requests can share that same read, which is why batching raises throughput (session 3).

3 · On gpt-4.1 Kiln's mean request is 1,300 tokens in and 250 out. Roughly what share of the bill is output?

The widget prints an input share of 56.5%, so output is 43.5%. Output is one token in six, but at $8.00 against $2.00 per million it carries far more than its token share.
